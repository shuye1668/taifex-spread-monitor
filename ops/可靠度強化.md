# 家中主機發布鏈 — 可靠度強化 runbook

> 目的：根治「發布鏈靜默停擺、公開頁停更一個月卻無人察覺」的問題。
> 事故現象：`data` 分支最後發布停在 **2026-07-20 08:13（台北）**，之後整整一個月未更新。
> 根因：`台指期價差監控.py`／`pages_publish.py` 這條家中主機發布鏈中斷後，腳本只寫本機
> `pages_publish.log`、**不對外告警**，因此沒人知道。

本方案＝**保留家中 PC 抓資料（不脫離主機）**，但補上兩層防護：

| 層 | 位置 | 作用 |
|---|---|---|
| **① 自我復原** | 家中 PC（本文件） | 崩潰／重開機自動重啟，降低停擺發生率 |
| **② 外部告警** | GitHub（`taifex-spread-pages` 的 workflow） | 真的停擺時自動開 Issue 通知你，PC 全關也能示警 |

> 為什麼要留在家中 PC：核心台指期報價只有台灣來源（期交所 `mis.taifex.com.tw` 主、
> `ws.api.cnyes.com` 備援），這些來源會封鎖海外雲端 IP，GitHub Actions（美國 IP）抓不到；
> 且盤中每分鐘快照需長時間累積。故資料仍由家中台灣 PC 產生最單純可靠。

## ① 自我復原（家中 PC）

目標：**主程式** 與 **發布器** 都做到「開機自動跑、崩潰自動重啟、不必登入桌面」。

### 1-1. 主程式 `台指期價差監控.py` → 用 NSSM 設成服務（崩潰自動重啟）

工作排程器不會在程式「當掉但沒結束」時重啟它；NSSM 服務可以。安裝 NSSM 後：

```powershell
# 路徑請依你的實機調整（python 位置、程式所在資料夾）
nssm install SpreadMonitor "C:\Windows\py.exe" "C:\台指期監控\台指期價差監控.py"
nssm set SpreadMonitor AppDirectory "C:\台指期監控"
nssm set SpreadMonitor AppEnvironmentExtra SPREAD_HOST=127.0.0.1
nssm set SpreadMonitor Start SERVICE_AUTO_START
nssm set SpreadMonitor AppExit Default Restart          # 崩潰→自動重啟
nssm set SpreadMonitor AppThrottle 5000                 # 重啟節流 5 秒，避免瘋狂重啟
nssm start SpreadMonitor
```

驗收：`nssm status SpreadMonitor` 為 `SERVICE_RUNNING`；瀏覽器開 `http://127.0.0.1:8701` 有畫面。

> 已在用工作排程器跑主程式的話，先把那個舊任務停用，避免兩份同時搶 8701 埠。

### 1-2. 發布器 `pages_publish.py` → 工作排程器每 1 分鐘＋失敗重試

發布器本來就設計成「每次跑一輪就結束」，適合排程器每分鐘觸發。重點是把
**失敗自動重試** 與 **開機即啟用** 打開：

- 觸發：每 1 分鐘一次（沿用現況）。
- 一般：勾「不論使用者登入與否都執行」「以最高權限執行」。
- 設定頁：勾「如果工作失敗，每隔 1 分鐘重新啟動，最多 3 次」。
- 條件頁：**取消**「只有在電腦使用交流電時才啟動」「電腦閒置時才啟動」。
- 記得帶好環境變數（git 認證、`SPREAD_SERVER` 若非預設）。

> 若想更省事，也可把發布器改用 NSSM 常駐 `--loop` 模式（每 5 分鐘一輪、崩潰自動重啟），
> 與排程器二擇一即可，別同時開。

### 1-3. 兩個常被忽略的單點

1. **git push 認證（PAT）過期**：發布器日誌出現 `pushfail:` 就是它。用 fine-grained PAT
   （只授權 `taifex-spread-pages` 的 contents:write），存進 Windows 認證管理員；到期前更新。
2. **PC 睡眠/休眠**：確認電源計畫「永不睡眠」（你已用 `Set-NoSleep-PowerPlan` 設過）。

## ② 外部告警（GitHub 守門）

位置：公開 repo `taifex-spread-pages` 的 `.github/workflows/data-staleness-watch.yml`
（以 PR 形式交付，**合併進該 repo 的 `main` 後生效**）。

- 每 30 分鐘檢查 `data` 分支 `meta.json` 的發布時間戳。
- 資料 **超過 120 分鐘** 未更新 → 自動開一張 Issue（指派給 `shuye1668`，GitHub 寄信通知）。
- 資料恢復 → 自動關閉該 Issue。
- 零 secret、不碰任何台灣資料源，**PC 全關也能示警**。

合併後可到該 repo 的 Actions 分頁手動 `Run workflow` 觸發一次測試。
因目前資料早已停更 >120 分，會立刻開出一張示範 Issue；修好發布鏈、資料恢復後會自動關閉。

---

## ③ 停更時的復原 SOP

收到守門 Issue（或健檢報 RED）時，照這個順序：

1. 開 `http://127.0.0.1:8701` → 沒回應：主程式沒跑 → `nssm restart SpreadMonitor`。
2. 跑 `python pages_publish.py --status` → 看日誌最後幾行：
   - `略過：主監控伺服器未回應` → 回步驟 1。
   - `pushfail:` → git 認證問題 → 更新 PAT。
   - 沒有任何近幾分鐘的紀錄 → 排程器沒觸發 → 檢查工作排程器該任務是否被停用。
3. 修好後，`data/meta.json` 的 `publishedAt` 會跳到當下、公開頁底部橫幅由橘轉藍、守門 Issue 自動關閉。

## ④ 選配：直接 Email／手機推播（比 GitHub Issue 更即時）

GitHub 守門開 Issue 時 GitHub 會寄信給你，通常已足夠。若想要更即時的獨立通道，兩個低成本作法：

- **Gmail SMTP**（純標準庫 `smtplib`）：在發布器連續 N 輪 `pushfail`／`略過` 時寄信。
  需要一組 Gmail 應用程式密碼存環境變數（不寫進程式、不上傳）。
- **手機推播**（Pushover／ntfy 等）：守門或發布器改成 POST 一個 webhook。

需要的話我可以幫你把其中一種接進 `pages_publish.py` 或守門 workflow，開後續 PR。
